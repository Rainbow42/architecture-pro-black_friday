## Задание 7. Схемы собраний и выбор ключей шардирования

### 7.1. От чего я отталкивался при выборе ключа

Ключ шардирования — это поле или набор полей, по значению которых MongoDB решает, на какой шард положить документ. От него зависит почти всё: и равномерность раскладки данных, и то, попадёт ли запрос на один шард или уйдёт веером на все сразу.

Я проверял каждого кандидата по четырём признакам.

**Дробность.** У ключа должно быть много разных значений. Если взять раздел товара, значений будет десяток-другой, и мельче, чем «весь раздел целиком», данные уже не разложить.

**Равномерность.** Значения должны встречаться примерно одинаково часто. Раздел «Электроника» собирает 70 % обращений — если сделать ключом только его, один шард примет на себя почти всю нагрузку.

**Совпадение с запросами.** Если поле ключа есть в условии запроса, маршрутизатор `mongos` отправит запрос ровно на нужный шард (такой запрос называют адресным). Если поля нет — запрос уйдёт на все шарды сразу, и с ростом их числа станет только медленнее.

**Отсутствие постоянно растущего края.** Если ключ монотонно растёт (дата, `ObjectId`), все новые записи ложатся в один и тот же крайний диапазон, а значит — на один шард. Для собрания с частой записью это прямой путь к перегрузке.

Ещё три ограничения, которые я учитывал: поле ключа обязано быть проиндексировано, оно должно присутствовать в каждом документе, а менять сам ключ после запуска дорого (до версии 5.0 — только через перезаливку данных, начиная с 5.0 есть команда `reshardCollection`, но она надолго нагружает кластер).

### 7.2. Собрание `products` — товары

#### Структура документа

```json
{
  "_id": ObjectId("665f0c1a9b1e4d2f8c3a7e01"),
  "name": "Смартфон X 128 ГБ",
  "category": "electronics",
  "price": NumberDecimal("54990.00"),
  "attributes": {
    "color": "чёрный",
    "size": "6.1"
  },
  "stock": [
    { "geo_zone": "ekaterinburg", "quantity": 50 },
    { "geo_zone": "kaliningrad", "quantity": 30 }
  ],
  "updated_at": ISODate("2026-07-25T10:15:00Z")
}
```

| Поле | Тип | Назначение |
| --- | --- | --- |
| `_id` | ObjectId | Единственный опознаватель товара |
| `name` | String | Наименование |
| `category` | String | Раздел каталога |
| `price` | Decimal128 | Цена; для денег беру `Decimal128`, а не `Double`, чтобы не копить ошибку округления |
| `attributes` | Object | Дополнительные свойства: цвет, размер |
| `stock` | Array | Остаток по каждой геозоне |
| `updated_at` | Date | Время последнего изменения |

#### Основные операции

Частое уменьшение остатка при покупке, подбор товаров по разделу с отбором по диапазону цены и показ карточки товара по его опознавателю.

#### Кандидаты в ключ шардирования

| Кандидат | Сильная сторона | Почему не подходит или чем рискован |
| --- | --- | --- |
| `{ category: 1 }` | Подбор по разделу становится адресным | Дробность крайне низкая, «Электроника» целиком ложится на один шард — это ровно та авария, о которой говорится в задании 8 |
| `{ category: "hashed" }` | Хеш выравнивает разделы между собой | Все товары одного раздела дают одно значение хеша и попадают в один неделимый фрагмент; перекос только усилится |
| `{ _id: "hashed" }` | Идеально ровная раскладка, запись не упирается в край | Подбор по разделу уходит веером на все шарды; при отборе по цене это дорого |
| `{ category: 1, _id: 1 }` | Подбор по разделу адресный, при этом внутри раздела данные дробятся по `_id` и расходятся по шардам | Обращение только по `_id`, без раздела, станет веерным — приложение должно передавать раздел в условие |

#### Что предлагаю

Составной ключ `{ category: 1, _id: 1 }` с раскладкой по диапазонам.

Первая часть ключа даёт адресность: запрос «покажи технику для звука дешевле 10 000» уходит только на те шарды, где лежит этот раздел. Вторая часть спасает от неделимого куска: даже если в разделе миллион товаров, MongoDB разрежет его на множество фрагментов по `_id`, и балансировщик разнесёт их по разным шардам. Именно этого не умеет ни `{ category: 1 }`, ни `{ category: "hashed" }`.

Цену первой частью ключа я не брал сознательно: цены меняются, а ключ шардирования менять нельзя, и почти все товары столпились бы в узком ценовом диапазоне. Отбор по цене закрываю обычным составным указателем (индексом).

```javascript
sh.enableSharding("shop");

// указатель под ключ шардирования
db.products.createIndex({ category: 1, _id: 1 });

sh.shardCollection("shop.products", { category: 1, _id: 1 });

// указатель под подбор по разделу с отбором по цене
db.products.createIndex({ category: 1, price: 1 });

// указатель под остатки по геозонам
db.products.createIndex({ "stock.geo_zone": 1 });
```

Пример адресного запроса и списания остатка — раздел обязательно передаём в условии:

```javascript
// подбор по разделу с отбором по цене — уходит только на нужные шарды
db.products.find({ category: "audio", price: { $gte: 3000, $lte: 10000 } })
           .sort({ price: 1 })
           .limit(20);

// списание остатка: в условии есть обе части ключа шардирования
db.products.updateOne(
  {
    category: "electronics",
    _id: ObjectId("665f0c1a9b1e4d2f8c3a7e01"),
    stock: { $elemMatch: { geo_zone: "ekaterinburg", quantity: { $gte: 1 } } }
  },
  { $inc: { "stock.$.quantity": -1 }, $currentDate: { updated_at: true } }
);
```

Условие `quantity: { $gte: 1 }` здесь важно: оно не даёт увести остаток в минус при одновременных покупках, потому что проверка и изменение выполняются одной операцией над одним документом.

#### Что я бы улучшил на следующем шаге

Остаток меняется на порядки чаще, чем описание товара, но лежит в том же документе. Из-за этого каждая покупка переписывает документ целиком и мешает чтению каталога. Предлагаю со временем вынести остатки в отдельное собрание `product_stock` с ключом `{ product_id: "hashed" }` — тогда частая запись разойдётся ровно по всем шардам и перестанет мешать витрине. В рамках этого задания я оставляю единое собрание `products`, как описано в исходных требованиях, но считаю нужным зафиксировать эту мысль.

### 7.3. Собрание `orders` — заказы

#### Структура документа

```json
{
  "_id": ObjectId("665f0d2b9b1e4d2f8c3a7e42"),
  "customer_id": UUID("2f1c9a10-3b7e-4c55-9a21-0d4f7e8b1c33"),
  "created_at": ISODate("2026-07-25T12:40:11Z"),
  "items": [
    {
      "product_id": ObjectId("665f0c1a9b1e4d2f8c3a7e01"),
      "name": "Смартфон X 128 ГБ",
      "price": NumberDecimal("54990.00"),
      "quantity": 1
    }
  ],
  "status": "created",
  "total": NumberDecimal("54990.00"),
  "geo_zone": "moscow"
}
```

| Поле | Тип | Назначение |
| --- | --- | --- |
| `_id` | ObjectId | Опознаватель заказа |
| `customer_id` | UUID | Опознаватель покупателя |
| `created_at` | Date | Дата и время оформления |
| `items` | Array | Состав заказа с ценами на момент покупки |
| `status` | String | Состояние: `created`, `paid`, `shipped`, `done`, `cancelled` |
| `total` | Decimal128 | Сумма заказа |
| `geo_zone` | String | Геозона заказа |

Цены товаров я кладу внутрь заказа копией. Это сознательное дублирование: цена в каталоге завтра изменится, а в заказе она должна остаться такой, какой была в момент покупки.

#### Основные операции

Быстрое создание заказа с одновременным списанием остатка, показ истории заказов покупателя и показ состояния конкретного заказа.

#### Кандидаты в ключ шардирования

| Кандидат | Сильная сторона | Почему не подходит или чем рискован |
| --- | --- | --- |
| `{ created_at: 1 }` | История удобно читается по времени | Худший вариант для записи: все новые заказы идут в крайний диапазон, то есть на один шард — в распродажу он и ляжет |
| `{ geo_zone: 1, created_at: 1 }` | Заказы разложены по регионам | Дробность мала, Москва перевесит остальные регионы, внутри региона снова растущий край |
| `{ _id: "hashed" }` | Ровная запись | История покупателя собирается веером со всех шардов — а это одна из главных операций |
| `{ customer_id: "hashed" }` | Запись ложится ровно, история покупателя адресная | Внутри одного покупателя заказы не упорядочены по времени на уровне раскладки — решается обычным указателем |
| `{ customer_id: "hashed", created_at: 1 }` | То же плюс упорядоченность по дате внутри шарда | Требует MongoDB 4.4 и новее (составной ключ с хешем) |

#### Что предлагаю

Составной ключ с хешем `{ customer_id: "hashed", created_at: 1 }`.

Хеш по покупателю раскладывает записи ровно: два соседних заказа почти наверняка окажутся на разных шардах, растущего края нет вообще. При этом запрос истории содержит `customer_id`, то есть остаётся адресным — весь список заказов человека лежит на одном шарде и собирается одним обращением. Вторая часть ключа даёт упорядоченность по дате внутри шарда, поэтому «последние 20 заказов» читаются без лишней сортировки в памяти.

Если кластер младше версии 4.4, беру простой `{ customer_id: "hashed" }` и закрываю сортировку обычным указателем `{ customer_id: 1, created_at: -1 }` — разница по существу небольшая.

```javascript
db.orders.createIndex({ customer_id: "hashed", created_at: 1 });
sh.shardCollection("shop.orders", { customer_id: "hashed", created_at: 1 });

// показ состояния конкретного заказа
db.orders.createIndex({ _id: 1, status: 1 });
```

```javascript
// история покупателя — адресный запрос на один шард
db.orders.find({ customer_id: UUID("2f1c9a10-3b7e-4c55-9a21-0d4f7e8b1c33") })
         .sort({ created_at: -1 })
         .limit(20);
```

Отдельно отмечу слабое место: поиск заказа по одному лишь `_id` (например, из письма покупателю или из службы поддержки) уйдёт веером на все шарды. Чтобы этого избежать, я бы всегда передавал вместе с номером заказа и опознаватель покупателя — он есть и в личном кабинете, и в письме.

### 7.4. Собрание `carts` — корзины

#### Структура документа

```json
{
  "_id": ObjectId("665f0e3c9b1e4d2f8c3a7e77"),
  "owner_id": "2f1c9a10-3b7e-4c55-9a21-0d4f7e8b1c33",
  "owner_type": "user",
  "user_id": UUID("2f1c9a10-3b7e-4c55-9a21-0d4f7e8b1c33"),
  "session_id": null,
  "items": [
    { "product_id": ObjectId("665f0c1a9b1e4d2f8c3a7e01"), "quantity": 2 }
  ],
  "status": "active",
  "created_at": ISODate("2026-07-25T12:10:00Z"),
  "updated_at": ISODate("2026-07-25T12:31:00Z"),
  "expires_at": ISODate("2026-08-01T12:31:00Z")
}
```

| Поле | Тип | Назначение |
| --- | --- | --- |
| `_id` | ObjectId | Опознаватель корзины |
| `owner_id` | String | **Общий опознаватель владельца**: для гостя — значение `session_id`, для покупателя — `user_id` |
| `owner_type` | String | `guest` или `user` — чтобы не гадать, чей это опознаватель |
| `user_id` | UUID / null | Покупатель, если корзина уже привязана |
| `session_id` | String / null | Гостевой сеанс |
| `items` | Array | Состав: опознаватель товара и количество |
| `status` | String | `active`, `ordered`, `abandoned` |
| `created_at`, `updated_at` | Date | Время создания и последнего изменения |
| `expires_at` | Date | Время самоочистки старых корзин |

#### Основные операции

Создание корзины гостю или новому покупателю, получение текущей корзины по условию `{ session_id, status: "active" }` либо `{ user_id, status: "active" }`, добавление, замена и удаление товара, слияние гостевой корзины с корзиной покупателя при входе и отметка корзины как заказанной.

#### Главная сложность и как я её решаю

У корзины два разных пути поиска: по гостевому сеансу и по покупателю. Ключ шардирования один, и, какое поле ни возьми, половина обращений станет веерной. Проверять это на каждом обращении к корзине — а это самая частая операция на витрине — слишком дорого.

Поэтому я добавляю в документ поле `owner_id`, куда при создании корзины кладу либо `session_id` (для гостя), либо `user_id` (для вошедшего покупателя), а рядом — `owner_type`, чтобы значение всегда читалось однозначно. Оба пути поиска сводятся к одному полю, и оба становятся адресными.

| Кандидат | Сильная сторона | Почему не подходит или чем рискован |
| --- | --- | --- |
| `{ _id: "hashed" }` | Ровная раскладка | Оба основных поиска — по сеансу и по покупателю — становятся веерными |
| `{ user_id: "hashed" }` | Адресный поиск для вошедших | У гостей поля нет, все гостевые корзины лягут в общий диапазон значения `null` |
| `{ session_id: 1 }` | Адресный поиск для гостей | Для вошедших покупателей поиск веерный, плюс значения выдаются последовательно и дают растущий край |
| `{ owner_id: "hashed" }` | Оба поиска адресные, раскладка ровная | Требует дисциплины на стороне приложения: поле нужно заполнять всегда |

#### Что предлагаю

Ключ `{ owner_id: "hashed" }`.

```javascript
db.carts.createIndex({ owner_id: "hashed" });
sh.shardCollection("shop.carts", { owner_id: "hashed" });

// быстрый доступ к активной корзине владельца
db.carts.createIndex({ owner_id: 1, status: 1 });

// самоочистка брошенных корзин: документ исчезает по времени в expires_at
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 });
```

```javascript
// текущая корзина гостя — адресный запрос
db.carts.findOne({ owner_id: "sess_9f2c...", status: "active" });

// добавление товара
db.carts.updateOne(
  { owner_id: "sess_9f2c...", status: "active" },
  {
    $push: { items: { product_id: ObjectId("665f0c1a9b1e4d2f8c3a7e01"), quantity: 1 } },
    $currentDate: { updated_at: true }
  }
);
```

Слияние корзин при входе покупателя — единственная операция, которая затрагивает два шарда, потому что у гостевой и пользовательской корзины разные владельцы, а значит и разные значения хеша. Выполняю её в три шага и без общей сделки (транзакции) между шардами: читаю гостевую корзину, переношу её состав в корзину покупателя, отмечаю гостевую как `abandoned`.

```javascript
const guest = db.carts.findOne({ owner_id: "sess_9f2c...", status: "active" });

db.carts.updateOne(
  { owner_id: "2f1c9a10-3b7e-4c55-9a21-0d4f7e8b1c33", status: "active" },
  { $push: { items: { $each: guest.items } }, $currentDate: { updated_at: true } },
  { upsert: true }
);

db.carts.updateOne(
  { _id: guest._id, owner_id: guest.owner_id },
  { $set: { status: "abandoned" }, $currentDate: { updated_at: true } }
);
```

Операция редкая — раз за вход, а не раз за клик, — поэтому её стоимость я считаю приемлемой. Общая сделка между шардами здесь была бы дороже и надёжнее не стала бы: даже если последний шаг не выполнится, гостевая корзина просто останется активной и уйдёт по времени самоочистки.

Самоочистку по полю `expires_at` MongoDB выполняет на каждом шарде независимо, никакой особой настройки для разделённого кластера не требуется.

### 7.5. Сводка по трём собраниям

| Собрание | Ключ шардирования | Стратегия | Что даёт |
| --- | --- | --- | --- |
| `products` | `{ category: 1, _id: 1 }` | По диапазонам | Адресный подбор по разделу; популярный раздел дробится по `_id` и расходится по шардам |
| `orders` | `{ customer_id: "hashed", created_at: 1 }` | По хешу с упорядочиванием | Ровная запись без растущего края; история покупателя читается с одного шарда по дате |
| `carts` | `{ owner_id: "hashed" }` | По хешу | Оба пути поиска (гость и покупатель) адресные; ровная раскладка частой записи |

```javascript
// полный набор команд для разделения собраний
sh.enableSharding("shop");

sh.shardCollection("shop.products", { category: 1, _id: 1 });
sh.shardCollection("shop.orders",   { customer_id: "hashed", created_at: 1 });
sh.shardCollection("shop.carts",    { owner_id: "hashed" });

// проверка раскладки
db.products.getShardDistribution();
db.orders.getShardDistribution();
db.carts.getShardDistribution();
```

## Задание 8. Выявление и устранение «горячих» шардов

В распродажу один из шардов принял на себя перегрузку: на раздел «Электроника» приходилось 70 % обращений. Ниже — как я предлагаю такие перекосы замечать и что с ними делать.

### 8.1. Главная мысль: балансировщик выравнивает данные, а не нагрузку

Встроенный балансировщик MongoDB следит только за тем, чтобы объём данных на шардах был примерно одинаковым. Про то, сколько запросов приходит на каждый шард, он не знает ничего. Поэтому картина «данные разложены поровну, а один шард задыхается» — совершенно обычная, и сам собой этот перекос не исчезнет. Нагрузочный перекос надо замечать снаружи и лечить осознанно.

Отсюда два разных вида перекоса, и путать их не стоит.

**Перекос по данным** — на одном шарде заметно больше документов. Виден в `sh.status()` и `getShardDistribution()`, лечится балансировщиком, обычно сам.

**Перекос по нагрузке** — данных поровну, а обращения идут в один шард. Балансировщику не виден, лечится сменой ключа, зонами или кешем.

### 8.2. Набор метрик

| Метрика | Откуда берётся | О чём говорит | Порог, при котором я поднимаю тревогу |
| --- | --- | --- | --- |
| Операции чтения и записи в секунду по каждому шарду | `db.serverStatus().opcounters`, `mongostat` | Основной признак нагрузочного перекоса | Доля одного шарда выше 40 % при равном объёме данных, держится 10 минут |
| Доля веерных запросов | `db.serverStatus().shardingStatistics`, разбор `explain()`, записи маршрутизатора в журнале | Показывает, что ключ шардирования не совпадает с запросами | Больше 10 % запросов трогают все шарды |
| Задержка ответа, 95-й и 99-й процентили, по шардам | `mongotop`, сборщик показателей | Перегруженный узел отвечает заметно дольше остальных | 99-й процентиль одного шарда вдвое выше среднего по кластеру |
| Объём данных и число фрагментов на шард | `sh.status()`, `db.collection.getShardDistribution()` | Перекос по данным | Разница между шардами больше 20 % |
| Длина очереди запросов | `db.serverStatus().globalLock.currentQueue` | Узел не успевает обрабатывать поток | Очередь устойчиво больше нуля |
| Загрузка процессора и дисковых операций на узлах | Системный сбор показателей | Упирается ли шард в железо | Загрузка выше 70 % дольше 15 минут |
| Попадание в кеш WiredTiger | `db.serverStatus().wiredTiger.cache` | Рабочий набор перестал помещаться в память | Доля попаданий ниже 90 % |
| Отставание вторичных узлов | `rs.printSecondaryReplicationInfo()`, `rs.status()` | Первичный узел не справляется с потоком записи | Отставание больше 10 секунд |
| Неделимые фрагменты | `sh.status()`, отметка `jumbo` | Фрагмент нельзя разрезать — обычно беда с ключом | Появление хотя бы одного |
| Число переносов фрагментов и ошибки балансировщика | `config.changelog`, `config.actionlog` | Балансировщик не справляется или отключён | Переносы идут непрерывно либо не идут вовсе при перекосе |
| Распределение обращений по значениям ключа | Своя телеметрия приложения | Показывает ту самую «Электронику» с её 70 % | Доля одного значения выше 30 % |

Последнюю метрику подчеркну отдельно: её нет в самой базе, её должно считать приложение. Без неё видно, что шард горит, но не видно, из-за чего именно.

Собирать всё это удобно связкой `mongodb_exporter` и Prometheus, а оповещения описывать правилами примерно такого вида:

```yaml
- alert: НеравномернаяНагрузкаНаШард
  expr: |
    max by (shard) (sum by (shard) (rate(mongodb_op_counters_total[5m])))
      / scalar(sum(rate(mongodb_op_counters_total[5m]))) > 0.4
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "Один шард принимает больше 40 % операций кластера"
```

Полезные команды для разбора вручную:

```javascript
// как разложены данные по шардам
db.products.getShardDistribution();

// сводка по кластеру: шарды, фрагменты, состояние балансировщика
sh.status();

// сколько данных и фрагментов у каждого шарда (MongoDB 6.0 и новее)
db.getSiblingDB("admin").aggregate([ { $shardedDataDistribution: {} } ]);

// какие шарды затронул конкретный запрос
db.products.find({ category: "electronics" }).explain("executionStats").shards;

db.currentOp({ "secs_running": { $gte: 1 }, "op": { $ne: "none" } });

use config;
```

### 8.3. Чем выравнивать нагрузку

**Зоны — основной приём для нашего случая.** Зона привязывает диапазон значений ключа к определённым шардам. Популярный раздел можно развести по нескольким выделенным шардам, а остальные разделы оставить на прочих.

```javascript
// два шарда отдаём под «Электронику»
sh.addShardToZone("shard1", "hot");
sh.addShardToZone("shard2", "hot");
sh.addShardToZone("shard3", "regular");

sh.updateZoneKeyRange(
  "shop.products",
  { category: "electronics", _id: MinKey },
  { category: "electronics", _id: MaxKey },
  "hot"
);
```

**Ручное дробление и перенос фрагментов.** Быстрое лекарство, когда перегрев уже случился, а перестраивать ключ некогда.

```javascript
sh.splitFind("shop.products", { category: "electronics" });

sh.moveChunk(
  "shop.products",
  { category: "electronics", _id: ObjectId("665f0c1a9b1e4d2f8c3a7e01") },
  "shard3"
);
```

**Уточнение ключа шардирования.** Если ключ оказался слишком крупным — например, при запуске взяли только `{ category: 1 }`, — к нему можно добавить поле. Данные при этом не переписываются, но новое поле должно продолжать существующий ключ, а не заменять его.

```javascript
db.adminCommand({
  refineCollectionShardKey: "shop.products",
  key: { category: 1, _id: 1 }
});
```

**Полная перекладка собрания.** Начиная с версии 5.0 ключ можно сменить целиком. Приём тяжёлый: кластер переписывает собрание и заметно нагружается, поэтому только в спокойное время и никак не в распродажу.

```javascript
db.adminCommand({
  reshardCollection: "shop.products",
  key: { category: 1, _id: 1 }
});

// наблюдение за ходом перекладки
db.adminCommand({ currentOp: 1, "type": "op", "desc": /ReshardingDonor|ReshardingRecipient/ });
```

**Настройка балансировщика.** Окно работы стоит сдвинуть на ночь, чтобы переносы фрагментов не накладывались на дневную нагрузку, а размер фрагмента уменьшить, если данные дробятся плохо.

```javascript
use config;
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "01:00", stop: "06:00" } } },
  { upsert: true }
);

db.settings.updateOne(
  { _id: "chunksize" },
  { $set: { value: 64 } },
  { upsert: true }
);

sh.getBalancerState();
sh.isBalancerRunning();
```

**Кеш и вторичные узлы.** Часть чтений по популярному разделу закрываю Redis (он уже есть в стенде из заданий 2–4), а тяжёлые витринные выборки увожу на вторичные узлы — подробности в задании 9. Это не выравнивает раскладку, но снимает с горячего шарда заметную долю чтений и часто помогает быстрее всего остального.

**Увеличение числа реплик у горячего шарда.** Если перегрев дают именно чтения, к группе репликации горячего шарда добавляю ещё узлы и распускаю чтения по ним.

### 8.4. Порядок действий, когда шард уже горит

Сначала смотрю на `sh.status()` и `getShardDistribution()` и отвечаю на вопрос, какой это перекос — по данным или по нагрузке. Если по данным, проверяю, включён ли балансировщик, и не мешает ли ему окно работы. Если по нагрузке, по телеметрии приложения нахожу значение ключа, которое даёт основную долю обращений.

Дальше действую по возрастанию тяжести: включаю или расширяю кеширование горячих товаров, увожу читающие операции на вторичные узлы, разрезаю и переношу фрагменты вручную, настраиваю зоны, и только в спокойное время, если ничего не помогло, перекладываю собрание с новым ключом.

Отдельно фиксирую вывод для нашего случая: ключ `{ category: 1, _id: 1 }` из задания 7 уже снимает основную часть проблемы, потому что «Электроника» дробится по `_id` и расходится по шардам, а не лежит одним куском. Зоны нужны, если и после этого раздел перегревает конкретные узлы.

### 8.5. Что делать заранее

Считать в приложении распределение обращений по значениям ключа шардирования и держать его на виду. Проверять новый ключ на копии рабочих данных до запуска. Держать оповещения по доле операций на шард и по доле веерных запросов. Раз в спринт смотреть на `sh.status()` и на список неделимых фрагментов.

## Задание 9. Чтение со вторичных узлов и согласованность

Каждый шард у нас — группа репликации из трёх узлов: один первичный (`PRIMARY`) и два вторичных (`SECONDARY`). Запись всегда идёт на первичный, а вот чтение можно уводить на вторичные и тем самым разгружать кластер. Плата за это — отставание: вторичный узел применяет изменения не мгновенно, и читатель может увидеть картину, которой уже несколько секунд.

Вопрос в каждом случае один: что хуже — лишняя нагрузка на первичный узел или устаревшие данные перед глазами покупателя.

### 9.1. Чем это настраивается

**Предпочтение чтения** (`readPreference`) — куда направлять запрос. Нас интересуют три значения: `primary` — только первичный узел, всегда свежие данные; `primaryPreferred` — первичный, но при его недоступности вторичный; `secondaryPreferred` — вторичные, а если их нет, то первичный.

**Ограничение отставания** (`maxStalenessSeconds`) — не читать с узла, который отстал сильнее указанного. Здесь есть важная тонкость: MongoDB не принимает значение меньше 90 секунд. То есть требование «отставание не больше 5 секунд» драйвером не обеспечить — его нужно держать наблюдением и оповещениями, а если 5 секунд действительно критичны, читать с первичного узла.

**Уровень чтения** (`readConcern`) — насколько подтверждёнными должны быть прочитанные данные. Для денег и остатков беру `majority`: такие данные уже приняты большинством узлов и не пропадут при смене первичного узла.

**Причинно-согласованные сеансы** (causal consistency) — приём, при котором пользователь после собственной записи гарантированно видит её результат даже при чтении со вторичного узла. Полезен там, где хочется разгрузить первичный узел, но нельзя показать человеку его же устаревшие данные.

### 9.2. Таблица операций чтения

| Собрание | Операция чтения | Откуда читаем | Допустимое отставание | Обоснование |
| --- | --- | --- | --- | --- |
| `products` | Подбор товаров по разделу с отбором по цене | `secondaryPreferred` | до 10 с | Витрина каталога, самый частый запрос на витрине; цена и состав раздела меняются редко, устаревание на секунды покупатель не заметит |

### 9.3. Допустимое отставание: как я к нему отношусь

Для витрины каталога считаю приемлемым отставание до 10 секунд. Покупатель не отличит цену, изменённую 8 секунд назад, от текущей, а выигрыш в разгрузке первичных узлов при этом заметный.

Для остатков в карточке товара держу порог 5 секунд и слежу за ним оповещением. Число на витрине справочное, но чем оно ближе к правде, тем меньше разочарований при оформлении.

Для отчётов и выгрузок допускаю до 5 минут: они и так считают данные за сутки или за неделю.

Для всего, что связано с деньгами, остатками при оформлении, корзинами и только что совершёнными действиями покупателя, допустимое отставание — ноль, читаем только с первичного узла.

Ещё раз про ограничение: `maxStalenessSeconds` меньше 90 секунд MongoDB не примет, поэтому пороги в 5 и 10 секунд обеспечиваются не драйвером, а наблюдением. Если отставание вырастет, я предпочту заметить это по оповещению и увести чтения обратно на первичные узлы, чем полагаться на настройку, которая таких значений не поддерживает.

```javascript
// каталог: читаем со вторичных узлов
db.getMongo().setReadPref("secondaryPreferred");
db.products.find({ category: "audio", price: { $lte: 10000 } });

// проверка остатка при оформлении: только первичный узел и подтверждённые данные
db.getMongo().setReadPref("primary");
db.products.find({ category: "electronics", _id: productId })
           .readConcern("majority");

// причинно-согласованный сеанс: после своей записи видим свои же данные
const session = db.getMongo().startSession({ causalConsistency: true });
const carts = session.getDatabase("shop").carts;
carts.updateOne({ owner_id: ownerId, status: "active" }, { $push: { items: item } });
carts.findOne({ owner_id: ownerId, status: "active" });
```

Строка подключения для приложения, где основная часть чтений уходит на вторичные узлы, а запись подтверждается большинством:

```
mongodb://mongos_router:27020/shop?readPreference=secondaryPreferred&maxStalenessSeconds=90&w=majority
```

Наблюдение за отставанием:

```javascript
rs.printSecondaryReplicationInfo();
rs.status().members.forEach(m => print(m.name, m.stateStr, m.optimeDate));
```

### 9.4. Короткий вывод

Всё, что человек только что изменил сам, и всё, что связано с деньгами и остатками, читаем с первичного узла. Всё, что человек только рассматривает — каталог, описания, старую историю заказов, — читаем со вторичных. Корзина, вопреки первому впечатлению, целиком относится к первой группе: она меняется тем же пользователем в том же сеансе, и любое отставание там оборачивается пропавшим товаром.

## Задание 10. Переход на Cassandra

В распродажу магазин упёрся в неприятное свойство разделения по диапазонам: при добавлении новых шардов MongoDB принялась перекладывать данные между всеми узлами, и на пике это дало рост задержек. Руководство решило перевести часть данных в Cassandra ради трёх вещей: отказоустойчивости без выделенного главного узла, быстрого расширения кластера без полной перекладки данных и ровного распределения.

Ровное расширение в Cassandra получается за счёт того, что данные разложены по кольцу опознавателей, а каждый узел отвечает за множество мелких участков этого кольца (виртуальные узлы). Новый узел забирает себе часть участков у нескольких соседей сразу — переезжает лишь малая доля данных, остальные остаются на месте. Полной перекладки, из-за которой у нас просели задержки, не происходит.

### 10.1. Что переносим, а что оставляем

Сильные стороны Cassandra: очень быстрая запись, линейное расширение, работа в нескольких центрах обработки данных, отсутствие единой точки отказа. Слабые: нет сделок между разделами, нет соединения таблиц, согласованность в общем случае отложенная, произвольные выборки не поддерживаются — таблица проектируется под конкретный запрос.

| Данные | Решение | Обоснование |
| --- | --- | --- |
| История заказов | Переносим | Пишется один раз, читается по покупателю, объём растёт постоянно. Ровно тот случай, где Cassandra сильна: поток записи большой, выборка предсказуемая, соединения не нужны |
| История изменений состояния заказа | Переносим | Чистый поток событий, только добавление записей, чтение по одному заказу |
| Корзины и гостевые сеансы | Переносим | Огромный поток записи (каждый клик по кнопке «в корзину»), короткая жизнь, встроенное время жизни записи снимает задачу очистки. Потеря отдельной корзины при сбое не критична для денег |
| Просмотры товаров, поведенческие события | Переносим | Данных много, ценность каждой записи низкая, требования к согласованности мягкие |
| Остатки товаров | Оставляем в MongoDB | Здесь нужна проверка «есть ли товар» вместе с его списанием одной операцией. В Cassandra такой проверки в общем случае нет, а лёгкие сделки (`IF NOT EXISTS`, `IF quantity > 0`) работают через согласование между узлами и на пике дают заметную задержку. Риск продать недоступный товар выше выигрыша |
| Каталог товаров | Оставляем в MongoDB | Подбор по разделу с отбором по диапазону цены, сортировкой и разбиением на страницы — это произвольные выборки. Под каждый такой запрос в Cassandra пришлось бы заводить отдельную таблицу |
| Оформление заказа как денежная операция | Оставляем в MongoDB | Нужна связка «списать остаток и создать заказ» в одной сделке |

Коротко: в Cassandra уходит то, что пишется потоком и читается по заранее известному опознавателю. В MongoDB остаётся то, где нужны проверки перед записью и произвольные выборки.

### 10.2. Модель данных

В Cassandra таблица строится под запрос, а не под сущность, поэтому одни и те же заказы у меня лежат в двух таблицах. Дублирование здесь — норма, а не ошибка проектирования.

Первичный ключ состоит из двух частей. **Ключ раздела** определяет, на какие узлы попадёт запись, и по нему обязательно должно быть равномерное распределение. **Ключи кластеризации** задают порядок записей внутри раздела и позволяют читать их отрезками.

#### Пространство ключей

```sql
CREATE KEYSPACE shop
WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'dc_msk': 3,
  'dc_ekb': 3
};
```

Три копии в каждом центре обработки данных — обычный выбор: позволяет работать с уровнем согласованности `LOCAL_QUORUM` (согласие двух узлов из трёх) и переживать потерю одного узла без остановки работы.

#### История заказов покупателя

```sql
CREATE TABLE shop.orders_by_customer (
    customer_id   uuid,
    period        text,        -- «ведро» вида '2026-07'
    created_at    timestamp,
    order_id      uuid,
    status        text,
    total         decimal,
    geo_zone      text,
    items         list<frozen<order_item>>,
    PRIMARY KEY ((customer_id, period), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);
```

Ключ раздела — покупатель вместе с месяцем. Опознаватель покупателя даёт высокую дробность и ровное распределение: заказы разных людей расходятся по всему кольцу. Месяц добавлен, чтобы раздел не рос бесконечно: у постоянного покупателя за годы накопятся тысячи заказов, а слишком большой раздел — это неравномерная нагрузка на узел и тяжёлое чтение. С месячным «ведром» размер раздела ограничен сверху, и обычный запрос «последние заказы» читает один-два раздела.

Ключи кластеризации — время создания по убыванию и опознаватель заказа. Убывающий порядок означает, что самые свежие заказы лежат в начале раздела и читаются без сортировки.

```sql
-- последние заказы покупателя за текущий месяц
SELECT * FROM shop.orders_by_customer
WHERE customer_id = 2f1c9a10-3b7e-4c55-9a21-0d4f7e8b1c33
  AND period = '2026-07'
LIMIT 20;
```

#### Заказ по опознавателю

```sql
CREATE TABLE shop.orders_by_id (
    order_id      uuid PRIMARY KEY,
    customer_id   uuid,
    created_at    timestamp,
    status        text,
    total         decimal,
    geo_zone      text,
    items         list<frozen<order_item>>
);
```

Отдельная таблица под запрос «покажи заказ по его номеру» — из письма покупателю или из службы поддержки. Ключ раздела здесь сам заказ, дробность максимальная, распределение идеально ровное.

#### История состояний заказа

```sql
CREATE TABLE shop.order_status_history (
    order_id    uuid,
    changed_at  timestamp,
    status      text,
    comment     text,
    PRIMARY KEY ((order_id), changed_at)
) WITH CLUSTERING ORDER BY (changed_at DESC);
```

Раздел на заказ, внутри — события по времени. Разделы маленькие (у заказа несколько смен состояния), распределение ровное.

#### Корзины

```sql
CREATE TYPE shop.order_item (
    product_id  uuid,
    name        text,
    price       decimal,
    quantity    int
);

CREATE TABLE shop.carts_by_owner (
    owner_id    text,        -- опознаватель покупателя либо гостевого сеанса
    owner_type  text,
    status      text,
    items       list<frozen<order_item>>,
    created_at  timestamp,
    updated_at  timestamp,
    PRIMARY KEY ((owner_id))
) WITH default_time_to_live = 604800;   -- 7 дней
```

Ключ раздела — тот же общий опознаватель владельца, что и в задании 7: и гостевой сеанс, и покупатель ложатся в одно поле, поэтому оба пути поиска попадают ровно в один раздел. Раздел крошечный — одна корзина. Время жизни записи в неделю снимает задачу очистки брошенных корзин: Cassandra удалит их сама.

#### Как я защищаюсь от перегретых разделов

Перегретый раздел в Cassandra возникает по той же причине, что и горячий шард в MongoDB: ключ раздела слишком крупный. Если бы я взял ключом раздел каталога или геозону, вся «Электроника» или вся Москва легли бы на одни и те же узлы — именно та авария, что описана в задании 8.

Поэтому все ключи раздела у меня построены на опознавателях с высокой дробностью: покупатель, заказ, владелец корзины. Там, где раздел мог бы разрастись со временем, добавлено «ведро» по месяцу. Для очень крупных покупателей, если такие появятся, тем же приёмом можно добавить в ключ ещё и номер части раздела.

Смена состава кластера при такой модели проходит спокойно: разделы мелкие и равномерно разбросаны по кольцу, новый узел забирает свою долю участков у нескольких соседей, полной перекладки данных не происходит. Это и есть то, чего не хватало при разделении по диапазонам в MongoDB.

### 10.3. Стратегии восстановления целостности

Данные в Cassandra лежат в нескольких копиях, и после сбоев копии расходятся. Есть три способа их снова свести.

**Подсказки при недоступности узла** (Hinted Handoff). Если узел-копия недоступен, узел-распорядитель запоминает изменение у себя и доставляет его, когда сосед вернётся. Работает по умолчанию, окно хранения подсказок — три часа. Помогает при коротких сбоях: перезапуск узла, потеря связи на минуту. При долгом отсутствии узла подсказки перестают накапливаться, и одного этого способа уже мало.

**Починка при чтении** (Read Repair). Во время чтения сравниваются ответы копий, и расхождения исправляются на месте. Даром лечит именно те данные, которые кто-то читает, — то есть самые нужные. Данные, к которым не обращаются, так и остаются разошедшимися.

**Плановая сверка** (Anti-Entropy Repair, `nodetool repair`). Узлы строят по своим данным деревья свёрток и сравнивают их между собой, после чего переносят только различающиеся куски. Это единственный способ, который приводит в порядок и те данные, которые никто не читает. Обязателен к регулярному запуску — реже, чем `gc_grace_seconds` (по умолчанию 10 дней), иначе удалённые записи могут «воскреснуть»: метка об удалении будет вычищена раньше, чем доедет до всех копий.

| Сущность | Основной способ | Дополнительно | Уровень согласованности | Обоснование |
| --- | --- | --- | --- | --- |
| Заказы (`orders_by_customer`, `orders_by_id`) | Плановая сверка раз в неделю | Подсказки, починка при чтении | Запись и чтение `LOCAL_QUORUM` | Денежные данные: потеря заказа недопустима. Согласие большинства при записи и чтении гарантирует, что прочитаем именно записанное. Плата — чуть более высокая задержка, для оформления заказа это приемлемо |
| История состояний заказа | Плановая сверка раз в неделю | Подсказки | Запись `LOCAL_QUORUM`, чтение `LOCAL_ONE` | Запись важна, а чтение терпит: если человек на долю секунды увидит предыдущее состояние, ничего страшного не произойдёт. Чтение с одного узла заметно быстрее |
| Корзины | Плановая сверка раз в 3–5 дней | Подсказки, починка при чтении | Запись и чтение `LOCAL_QUORUM` | Покупатель читает корзину сразу после того, как её изменил, поэтому нужна согласованность на чтении. Сверку делаю чаще из-за времени жизни записей: удаления должны разойтись по копиям до вычистки меток |
| Гостевые сеансы, просмотры товаров | Подсказки | Починка при чтении изредка | Запись и чтение `LOCAL_ONE` | Ценность отдельной записи низкая, зато объём огромный. Здесь важнее скорость и дешевизна записи, чем полная сходимость копий; плановую сверку по таким таблицам можно не гонять вовсе |

Настройка починки при чтении и запуск плановой сверки:

```sql
ALTER TABLE shop.orders_by_customer WITH read_repair = 'BLOCKING';
ALTER TABLE shop.carts_by_owner WITH gc_grace_seconds = 259200;   -- 3 дня
```

```shell
# плановая сверка по одному пространству ключей, только свой центр обработки данных
nodetool repair -pr -local shop

# состояние узлов кольца
nodetool status
```

Смысл выбора в одной фразе: чем выше уровень согласованности, тем меньше риск прочитать устаревшую копию и тем выше задержка. Для заказов и корзин я плачу задержкой за надёжность, для сеансов и просмотров — наоборот, соглашаюсь на возможное расхождение ради скорости.

## Итоги

По заданию 7 предложены три ключа шардирования: `{ category: 1, _id: 1 }` для товаров, `{ customer_id: "hashed", created_at: 1 }` для заказов и `{ owner_id: "hashed" }` для корзин. Для корзин при этом введено общее поле владельца, которое сводит два разных пути поиска к одному адресному запросу.

По заданию 8 главный вывод такой: балансировщик выравнивает объём данных, но не нагрузку, поэтому перекос по обращениям надо ловить своими метриками — прежде всего долей операций на шард и распределением обращений по значениям ключа. Лечится он зонами, ручным переносом фрагментов, кешем и, в крайнем случае, перекладкой собрания.

По заданию 9 граница проведена так: всё, что покупатель только что изменил, и всё, что связано с деньгами и остатками, читается с первичного узла; каталог, описания и старая история — со вторичных.

По заданию 10 в Cassandra уходят история заказов, история их состояний, корзины и поведенческие события, а остатки и каталог остаются в MongoDB. Ключи разделов построены на дробных опознавателях с «ведром» по месяцу там, где раздел может разрастись, — так расширение кластера не приводит к полной перекладке данных.
